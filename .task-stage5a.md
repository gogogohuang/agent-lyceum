# Approval gate stage 5a: read-only `approvals` commands, approval screen, reject

## Scope
Implement the READ-ONLY half of task 5 of spec `docs/superpowers/specs/2026-11-13-approval-gate-design.md` §10. Read §4.5 (state machine), §4.6 (approval screen), §4.8 (audit), §4.10 (CLI), §5, §6, §9 and `docs/approval-store-api.md` first. Everything stays off by default: with no `executors.yaml`, behaviour and output must stay byte-identical to before. Existing modules to reuse, not reinvent: `src/approval-state.ts`, `approval-transition.ts`, `approval-display.ts`, `approval-json.ts` (`schema_version: 1`, do not change the schema), `approval-liveness.ts`, `approval-store.ts`, `approval-types.ts`; the `approvals collect --call` subcommand already exists in `src/cli.ts` (extend that command group, do not duplicate it).

1. `approvals list [--all] [--json]`: default lists only `pending` and not yet expired, STRICTLY read-only (a request past `expires_at` or whose creator is dead is shown with a computed state such as "expired (not yet recorded)", and nothing is written). `--all` lists every state and is allowed to write `expired` / `unknown` through the exclusive `link` transition (race with another writer: exactly one wins). `--json` carries `schema_version`.
2. `approvals show <id>` (id = unique prefix of at least 8 characters): strictly read-only. Screen per §4.6: the three zones (agent-stated summary marked unverified; executor name with `command[0]` realpath and sha256; the full payload), each payload line prefixed with `│ `, paged at most 4096 bytes per page cut on character boundaries (an over-long line wraps on a character boundary without changing content), plus id, proposer, times, expiry, payload sha256 first 16 hex, and other requests with the same payload hash (id, state). The payload is shown verbatim (no rewriting).
3. `approvals audit <id>`: strictly read-only, lists `record.json` facts and `state/<n>.json` events in sequence order.
4. `approvals reject <id> [--reason]`: `pending` to `rejected` (terminal) via exclusive `state/<n+1>.json` creation; non-`pending` is refused; concurrent `reject` and `approve`-style races have exactly one winner. Actor identity (user, TTY, pid, process start time) is recorded; a non-TTY invocation or a wrong or ambiguous id prefix is refused.
5. One shared sanitiser used by `list`, `show` and `audit` for external text (executor stdout/stderr and error messages): strip ESC sequences, C0/C1 control characters (keep newline), `Cf` characters, convert `\r` to a visible mark. Payload, summary and file names are NOT rewritten (they were already rejected by the allow-list at collection).
6. All commands: `schema_version` only on `list --json`; a corrupt highest `state/<n>.json` fails closed (all transitions refused, `show` and `list` mark it as corrupted); nothing here may spawn an executor.
7. Tests under `test/`, using `fault()` crash injection where earlier stages did: state-machine rows for `reject` and lazy `expired`; `show`/`audit`/default `list` write nothing (assert directory state is unchanged); concurrent `list --all` writers produce one `expired`; clock rollback; sanitiser with ESC, `\r`, `Cf`, forged box-drawing; paging boundaries including a line over 4096 bytes; id-prefix handling; `COMMANDS` in the web console contains no `approvals.*` (extend the existing coverage test pattern). Unenrolled behaviour byte-identical: extend existing compat tests, do not regenerate fixtures.
8. Docs: `docs/commands.md` and `commands.zh-TW.md` (keep pairs in sync), `docs/approval-store-api.md`; `npm run check:docs` must pass.

## Acceptance criteria

- With no `executors.yaml`, all existing byte-for-byte compat tests pass unchanged.
