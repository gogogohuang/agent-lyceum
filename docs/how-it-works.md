# How a run works

1. The task (text, or a copy of `--task-file` kept read-only as `runs/<id>/task.md`) becomes the first mail to the lead. Tasks ≤ 16 KB are inlined; larger ones are passed by reference. Files over 1 MB are rejected.
2. The dispatcher wakes whichever agent has unread mail with `claude -p` or `codex exec` (headless). Each wake-up is a fresh session unless `resume: true`.
3. Every wake-up prompt contains the agent's `AGENT.md`, the team protocol, `COMMON.md` (read-only, ≤ 8 KB), the project records (see below), the `MEMORY.md` index of each memory dir, the **oldest** unread message (body within the budget below; one message per wake-up; the lead instead takes a run of up to 5 `reply`/`failure` messages at once, and any other agent takes up to 5 consecutive `reply`/`failure` messages of the same thread, and decides on them together), and titles of the queued ones, which stay unread until their own wake-up. The mail body shown in the prompt is limited to 16 KiB per message and 64 KiB for all of a wake-up's messages (headers and the truncation marker are not counted); a longer body is cut at a UTF-8 character boundary and followed by a line with its original file path. The mail file itself is not changed.
   **Project records:** the lead writes each decision or lesson as its own file, `shared/common/records/decisions/<id>.md` or `records/lessons/<id>.md` (`id` = file name without `.md`: lowercase letters, digits, `-`). Frontmatter: `status: active|superseded` (required), `date: YYYY-MM-DD` (required), `title` (required), `run` and `supersedes` (optional; `supersedes` lists ids of the same kind); the body is the decision or lesson and why. Only the lead writes records (it may flip `status`); a change by any other agent is reverted and reported as a violation. Each decision or lesson is its own file, so concurrent runs that add new entries with distinct ids do not edit the same file; two runs editing the same entry can still collide. The prompt shows the effective-active entries (`status: active` and not named in another entry's `supersedes`), newest first by date then id, whole entries only, up to about 6 KB per kind; entries that do not fit are listed one per line with their path, to read on demand. Nothing is shown when there are no entries. The lead's `done` is rejected while a kind's effective-active entries exceed 6 KB; marking entries `superseded` or merging them fixes it. `records/.archive/` holds `tidy` output and is never shown.
4. Agents send mail by writing a Markdown file with frontmatter (`to`, `type`, `subject`) into **their own** `outbox/`. The dispatcher checks `can_message`, stamps the real sender, and moves it to the recipient's `inbox/`. Handled mail goes to `inbox/<agent>/read/`. Mailboxes belong to one run (`runs/<run-id>/mail/`), so mail never crosses runs. Runs started by older versions keep using the shared `shared/{inbox,outbox}/` mailboxes (their mail is never moved); resuming such a run shows that legacy layout.
   The body of every `task` and `reply` should carry fixed `##` headings (injected into each agent's prompt): `task` → `Goal`, `Acceptance criteria`, `Scope`, `Upstream`; `reply` → `Changes`, `Verification`, `Open items`, `Risks` (write `None` when empty; `done` is exempt). A `task` or `reply` missing a heading is sent back to its sender (a `failure` mail names the missing headings), at most twice per sender, type and subject in a run; after that it is delivered with a warning note prepended and a `format-warning` entry in the run log. Runs of the legacy layout always deliver with the warning.
5. The run ends when the lead sends `type: done`, when all mailboxes are empty, or after `max_rounds` wake-ups when you set a limit (the default `0` means no limit). A `done` must declare `outcome: completed|partial|blocked|failed` in its frontmatter and carry `## Result`, `## Files`, `## Verification`, `## Not done`; `completed` also needs every `## Steps` item ticked. A `done` that breaks this is sent back to the lead (twice at most, then it is kept as `partial`). Agent-lyceum does not verify what the lead reports. A failed wake-up is retried up to `retry` times (default 2, so 3 calls in all); if the agent still fails, the run stops (`agent_failed`, or `lead_failed` for the lead) instead of carrying on without it: the message it was handling stays unread, and the end message says how to look into the failure and how to continue (`agent-lyceum resume <run>` after fixing the cause, or `clear` to give up). When an agent is woken again for the same mail (a retry, or a redo after `resume`), its prompt carries a Retry or Redo notice and, if the earlier attempt left drafts in its `outbox/` that were never delivered, those drafts: shown only to that same agent, marked unverified, at most 4 KB, and never delivered. The prompt also asks the agent to read its task memory first. These are prompt requests; whether a model follows them has not been verified with a real runtime. Mail that repeats an earlier mail from the same sender to the same recipient (same type, reply target and text, whitespace aside) is not delivered again: the sender is told, which keeps two agents from looping on the same message.

Members with pending mail wake in parallel, with no cap, and never alongside the lead. Where they work depends on the folder; see [Several runs at once](#several-runs-at-once). A worktree isolates files only: it cannot isolate side effects on external services, databases or the network.

## Several runs at once

Concurrency needs no configuration, and any number of runs of one project can be active at once, as long as each has its own worktree. What a new run (a solo `run --agent <name>` included) does depends on the folder:

- **Git repo with a commit (default `files` ref storage):** **every** run works in its own git worktree: the lead in `projects/<name>/worktrees/<run-id>/<lead>` on branch `agent-lyceum/<run-id>/<lead>`, each member in a worktree cut from the lead's. A run starts from your repo's `HEAD`, so your uncommitted changes are allowed and are **not** part of it (the start line says how many files that is). Your working tree, index and HEAD are never touched, and the result is **not** written into your working tree: take it with `git merge <branch>` or `open_pr`.
- **Non-git folder, a repo with no commit, or a repo using reftable:** the run works directly in the folder, one agent at a time, and prints an info line with the reason instead of an error. Only one such run can be active; starting a second is refused and names the run in the way. Runs with their own worktrees can run beside it.
- **Conflicts:** if two agents of a run change the same file, the later one's change is refused, its branch is kept and the lead is told. Changes that do not fit together across different files are not detected.

- **Ending:** when a run ends (done, cancelled, failed, idle or round limit), the lead's work is committed once on its branch and written as `runs/<run-id>/lead.patch`, and the run prints `git merge <branch>`. A run that stops to ask you (`waiting`) is not finished: nothing is committed and no merge hint is printed; its work stays in the lead's worktree and `resume` continues in the same one.
- **Decided at start:** a run records whether its lead works in a worktree (`lead_workspace` in its state). `resume` follows what the run was started with. A run started by an older version without that field resumes with its lead in the folder and its members in worktrees, all in parallel, if it was a parallel run; otherwise it works directly in the folder.
- **`tidy`:** `tidy` and `tidy --undo` need the project to themselves: they are refused while any run is active, and no run can start while they run.
- **`clear`:** `clear <run-id>` refuses while the lead's branch is not merged (use `--keep-worktrees` to keep it). A lock left by a crashed run is removed with `clear --lock [run-id] [-p name] --force`; with several locks, name the run.

Known limits:

- Agent processes are not capped: every member with pending mail wakes at once, in every active run.
- A lead with `can_edit_agent_md: true` edits the `CLAUDE.md`/`AGENTS.md` in its own worktree; the change reaches your repo only when you merge its branch.
- `COMMON.md` and the `AGENT.md` files are shared by all runs of the project. Each run's guard only judges what changes while its own agents are working, so an edit by one run is kept; but if two runs' wake-ups overlap in time, a change one makes while the other's agents are working can be reverted by the other.
- Two runs that edit the same file are for you to reconcile when merging; agent-lyceum never merges.

## Continuing a finished run

Every run has a **name**: made from the first line of the task (lowercase letters, digits and `-`, at most 30 characters; `task` if nothing usable is left; `-2`, `-3` on repeats), or chosen with `run --name <name>` (same characters and length; refused if the name is already used). `resume`, `clear` and `status --task-id` accept the full run id, the name, or a unique prefix of either; an ambiguous prefix lists the candidates and exits `1`, and an empty one is refused. `status` shows the name next to the id.

A finished (`done`) run can be reopened with a follow-up request: `agent-lyceum resume [run] "<follow-up>"` (or `--task-file f`). The lead gets the text as a new `task`, and the run goes on with the same run dir, task memory, sessions and lead worktree.

- **Which runs:** only a finished run can be reopened. A run that is still running is refused; a run that is not finished is refused when given text (resume it without text first). Without text nothing changes: a finished run just prints its result. Without a run, the candidates are the finished runs, newest first: exactly one is used, none is an error, and several are listed (in a terminal you pick one by number or name; without a terminal the command fails and lists them). A lone argument counts as follow-up text only when it cannot be a run reference (it contains whitespace or a character a run name cannot contain); a one-word follow-up needs `resume <run> "<text>"` or `--task-file`.
- **What is kept:** the follow-up is saved as `runs/<run-id>/followups/<n>.md`. Each `done` report is kept as `done-<n>.md`, and `result.md` is always the latest. `state.json` gains `name`, `reopened`, `round_floor` and `step_base` (all optional, so older runs still load). The progress (`## Steps`) carries on: the checklist at the reopen stays, and the steps the lead lists for the follow-up are added after it (a step it lists again only takes the new tick); for the follow-up's `completed` only its own steps must be ticked. Unresolved blocked integrations stay; the done-contract reminders start afresh for each reopened segment.
- **Round limit:** with a `max_rounds` set, it counts from the reopen: `rounds` keeps accumulating, and the limit is the rounds at reopen plus `max_rounds`.
- **The lead's branch** (runs with a lead worktree): if the branch was already merged into your `HEAD` and the lead worktree is clean and untouched since the run ended, the worktree and the branch (same name, `agent-lyceum/<run-id>/<lead>`) are re-cut from your current `HEAD`, and a line says so. Otherwise the same worktree and branch continue. If a pull request was already recorded (`pr_url`) and the branch was not re-cut, a new `open_pr: true` only pushes ("pull request updated") while that pull request is still open; if it was merged (a squash merge included) or closed, a new pull request is opened instead. If the branch was re-cut, the recorded `pr_url` is cleared (the old URL stays in the run's notes) and a new pull request is opened when asked. agent-lyceum still never merges.
- **Handoff notes:** before it sends `done`, the lead writes what a follow-up will need into `task-memory/<run-id>/_shared/` in the agent-lyceum home (`MEMORY.md` is the index): decisions and why, interfaces agreed, current state, what is left and the next steps, pitfalls met. Members can read this folder but not write it (a run started with `run --agent` has one agent, which is its own lead and writes it; `call` has none). Once a run is reopened, every wake-up of every agent gets `MEMORY.md` in its prompt (the first 8 KB; a longer index is cut and flagged), and the reopened `task` mail's `Upstream` names it; the first segment's prompts do not contain it. If the lead sends `done` without having changed `MEMORY.md` in that segment, the run is not blocked: a note `shared-not-updated` is added to the run's notes. `clear` deletes the folder with the task memory; `tidy` does not touch it. It holds notes about this task only; lessons that outlive it belong in project or global memory.

## Opening a pull request

When your task asks for a pull request, the lead puts `open_pr: true` in the frontmatter of its `done` report. If the run then ends `completed` and the lead's branch has changes, agent-lyceum — not an agent — pushes `agent-lyceum/<run-id>/<lead>` to `origin` and runs `gh pr create` against the repo's default branch, using the lead's report as the description (ending with `🤖 Opened by agent-lyceum`). The run result prints the PR URL, and `state.json` records it as `pr_url`. Only the lead can ask: nobody else can send `done`, and no agent's sandbox is loosened — `git push` and `gh` run outside it, with your own credentials.

- It needs a lead branch, so it works only when the run has its own worktree (a git repo with a commit). Otherwise the request is reported and skipped.
- A request that cannot be honoured (the run did not complete, no changes, no `gh`, no `origin`, push or `gh` failed) never changes how the run turned out. The run says why it was not opened and keeps the branch; when a push or `gh pr create` failed it also prints the commands to finish by hand.
- Opening a pull request publishes the lead's branch and report to `origin`. An agent that asks for one (`open_pr: true`) can therefore get anything it can read inside its sandbox onto the remote, so only ask for a pull request in a task when that is acceptable. The push and `gh pr create` run from your main repository, never inside the agent's worktree, because an agent can write that directory.
- agent-lyceum never merges and does not wait for CI or review. In a git repo with a commit, `doctor` tells you whether `gh` and `origin` are there (it does not check that `gh` is logged in).

## When a wake-up fails

Without a `fallback` chain (see [Fallback models](configuration.md#fallback-models)) a failed wake-up is retried on the same model up to `retry` times, whatever went wrong, and then the run stops. That is unchanged. With a chain, the failure is classified first:

| Kind | What happens |
|---|---|
| `rate_limit`, `quota` | No retry: switch to the next model at once, and mark the failed model as cooling down. |
| `timeout`, `network`, `crash` | Retry on the same model up to `retry` times, then switch. |
| `auth` | Stop. A login problem is not hidden by changing model. |
| `unknown` (not recognized) | Retry on the same model `retry` times, then stop. No switch. |

Details:

- **Backoff:** only with a chain, a retry on the same model waits 5 s, then 15 s, then 45 s, at most 60 s. Without a chain there is no wait.
- **Fresh session:** a switch starts a new session on the backup, with the usual retry notice added to the prompt, and unread mail is delivered again as for any wake-up. The failed attempt's undelivered outbox drafts are handed back to the same agent as unverified drafts (see above); nothing else from the failed model's output is passed on. If the backup already has its own session and the agent has `resume: true`, the switch continues that session instead of starting a new one. The backup's session is kept under `state.sessions` as `<agent>@<runtime>/<model>`; the primary keeps the plain agent name and is never given the backup's id.
- **Every wake-up starts at the primary,** unless the primary is cooling down. A model that failed with `rate_limit` or `quota` is skipped for `fallback_cooldown_sec` (default 300 s) by all wake-ups of the run, including parallel ones. The cooldowns are in `state.json`, so `resume` keeps them; a new run starts without any. If every model of the chain is cooling down, the whole chain is tried. Cooldowns are only recorded for agents that have a chain.
- **A call that switches is announced:** a line `<agent> falling back to <runtime>/<model> (<kind>)` is printed and a note is added to the run, warning that the failed model's side effects were not undone and may have happened.
- **When every model fails** the run stops as `agent_failed` or `lead_failed`, as before. `failure.tried` lists each model once, with its last failure, and the end message lists them in order and still shows how to `resume`.
- **Known limit:** Codex on a dead network keeps reconnecting until the wake-up times out, so it ends as `timeout`, not `network`. It is treated like any other timeout, so it is retried and then switched.
